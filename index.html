Where the core, the modules and the databases sit

The target layout for DP Groups on MeghaOS: what runs on each server, which parts talk to which, and where each database boundary is drawn.

15 showrooms~300 system users~10,000 bills a day4 legal entities10 business domains (A–J)
  • 1Each legal entity gets its own servers and its own database. That is the audit boundary.
  • 2Inside an entity, all transactional modules share one instance and one database, so a bill posts stock, tax, payment and GL together.
  • 3Group-wide concerns (masters, consolidated MIS, fleet management) run as separate services, and they talk to the entities only over HTTPS.
Layer by layer

A module is configuration, not a program

In MeghaOS an application module (Store front, Accounts and so on) is a set of objects, forms, rules, workflows and reports. That set is stored as rows in the core schema plus its own tables in the data schema. It ships as part of a blueprint (.mbp) and runs on the core engines. Each module therefore lives inside the database of the instance that runs it. Giving a module its own server would also mean giving it its own database, its own users and its own copy of every master it reads.

  • ↑Modules (top). Domains A–F, H and I from the requirement deck. Built once as the DP blueprint, then installed per company.
  • ·Core (middle). Java engines, identical on every server and upgraded together: auth, permissions and field-level security, metadata, CRUD, workflow, rules, approvals, tax, costing, stock, payment, GL, reports, webhooks.
  • ↓Roles (bottom). The same program started three ways. web serves users and can scale out. There is exactly one job runner per database, because scheduled jobs have no lock yet and two runners would send the same email twice. report reads from the replica so MIS queries never slow the tills.
  • GAudit & MIS runs on the report role within a company, and in group reporting across companies. J Mumbai corporate keeps its books in the entity that owns them and does consolidation in group reporting.

Scaling up

  1. CPU on the web pods goes above 65%.
  2. The pod autoscaler adds a web pod, up to 4.
  3. If no node has room, the node autoscaler starts a new EC2 node.
  4. The pod starts Spring Boot and reports ready on /actuator/health.
  5. The load balancer starts sending it requests.

Scaling down

  1. Load stays low for about 5 minutes.
  2. The autoscaler picks a web pod to remove. It never goes below 2.
  3. The load balancer stops sending that pod new requests.
  4. The pod finishes the requests it is already handling, then stops.
  5. The node autoscaler moves pods off a mostly empty node and shuts it down.

Festival peaks

Java takes time to start, so CPU-based scaling always lags a sudden rush. Before Dhanteras or Akshaya Tritiya, raise the minimum to 4 web pods on a schedule and lower it afterwards.

Releasing a new version

Pods are replaced one at a time, and a new pod is added before an old one is removed, so the tills never go offline. Database migrations run when the first new pod starts. Each migration must still work with the old version running alongside it.

Needed before this works

  • 1Kubernetes manifests or a Helm chart for web, job runner and report, with the autoscaler settings. The repo has only Dockerfile.api today.
  • 2Graceful shutdown (server.shutdown: graceful). Without it, removing a pod cuts off requests in flight, including a bill being submitted.
  • 3Readiness and liveness checks wired to the Spring Boot health groups.
  • 4forward-headers-strategy, so the app sees the real client address and HTTPS behind the load balancer.
  • 5Prometheus metrics, so scaling can follow request rate as well as CPU.
  • 6A lock for scheduled jobs. It is the only way to run a second job runner for high availability.

Still to decide

  2. Franchise (FOCO) billing: under Abhushan's GSTIN (case 1), or each franchisee with its own GSTIN and its own company (case 2).
  3. Customer master: per company, or a group master shared through the master service.
  4. When to build the outbox and message broker (NATS is on the platform roadmap). Inter-company flows need it before go-live.
  5. Which broker: NATS JetStream by default, with Kafka or RabbitMQ introduced if the need arises.
  6. Hosting the master service: a small MeghaOS instance of its own, or a purpose-built service.
